## 设计结论（direction）

采用保守场景：操作者在桌面工作区重复管理多专家任务，先扫描“谁需要行动、下一步是什么”，再查看已有交付。方向是克制、紧凑；沿用项目浅色令牌、任务列表、四个详情页签、原生模态与证据结构。记忆点是“续跑待核验”与“实现结果 / 必需检查 / 独立验收”三类证据互相呼应，避免把恢复误认为重做。正面对标 GitHub Checks 对暂停、检查运行及历史重新运行的区分；本产品额外说明实现专家和独立核验专家的不同责任。此为结构参照，未作外部产品实测。

用户直接授权“读屏可以不用考虑，200%缩放暂时也不考虑”优先于旧报告。两项均为 `user_deferred / not_in_current_scope`、`passed: null`，非当前阻断；不将旧未知或失败改为通过。未启动读屏软件或新增缩放测试。原脚本已有 CSS 缩放样本原样保留，只作补充技术输出，不用于本轮缩放或语音验收。

## 结构与状态（state_coverage）

主路径为列表发现待行动任务 → 待处理入口或列表进入详情 → 阅读暂停原因、行动者及不重复实现的说明 → 手动“续跑待核验” → 系统继续已提交结果的必需检查与独立核验。只有这一个主要恢复按钮；其他动作保留在任务操作。`missionResumeAction` 同时控制状态、责任、下一步、待办及 CTA，`missionActionActor` 为列表/待办/详情投影同一行动者。原 DTO 保存在传输证据，不篡改历史。

原 QA-LEGACY-01 的具体文本是“系统处理 · 无需你操作”“等待系统检查或核验，不重复执行实现”，却显示“续跑未完成任务”。同一旧状态输入现在显示“需要你手动续跑 · 系统随后检查与独立核验”“续跑待核验；不重复执行已完成的实现”，按钮为“续跑待核验”，说明任务当前暂停、系统不会自动推进。实际组件的列表、待办、详情及子任务行均有 DOM、输入、传输和截图记录。修复前后导出投影用同一保存输入执行；修复前 CTA 来自保留源码和 QA 报告，未冒称本轮重新捕获旧组件截图。

恢复必须保留当前确认计划及有效状态 cursor 关联、宿主 `can_resume=true`、已提交实现 run、无 running worker 与无环境阻塞。无占用/外来占用由宿主拒绝 DTO 驱动，前端不根据事件猜测资格。不匹配、未知、缺实现 run、环境、预算等待均不暴露核验续跑。手动暂停仍由用户自选，包括暂停已提交核验；不加入强制待办。点击只调用已有 `control_mission(resume)`，没有实现派发、增额、权限授予或自动恢复。宿主仍复核全部资格。

下游 DTO 期望与旧版兼容边界记录在 `dto-contract.json`：新的明确原因建议为 `verification_resume_required / actor=user`；当前 `mission.wait.v1` 的 `system_verification / actor=system / can_resume=true` 仅按已经获准的行动归一。Rust、占用校验、预算特殊准入及真实执行器修复属于下游，本任务没有修改或代签。
