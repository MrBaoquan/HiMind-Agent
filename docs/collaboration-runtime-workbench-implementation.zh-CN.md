# 架构决策提案：可持续沟通、动态组队与直观可视化的协作任务

日期：2026-11-17

状态：proposed；作为下一项功能的实施输入，尚未实施或验证

目标仓库：`F:/WebProjects/项目看板/himind-agent`
正式 ADR 编号：主会话实施时按目录最新编号分配；正式 ADR 按仓库约定使用英文，本文件作为中文产品与实施附件。

## 1. 背景与证据边界

用户要求合并解决三个问题：协作任务信息过多且不直观；启动后需要持续向协调 Agent 提出需求；团队应能根据实际工作在运行时派活，并尽可能并行。

2026-11-17 对主工作区进行了只读抽查。ADR-0029 已定义 Mission/Workflow 分层、需求入口、并行执行和状态投影。`src/mission/contract.rs` 已有计划版本、专家绑定和反馈契约，但 MissionFeedbackInput 明确为观察信息，不能等同于需求变更或授权。`src/mission/store.rs` 的 propose_plan_for_snapshot 拒绝在实现或验收尝试活跃时替换整个计划；follow-up 主要围绕失败修复及其范围约束。前端已有快照、等待原因和运行身份匹配逻辑。由此可复用现有基础，但不能声称完整运行时对话和动态计划调整已经具备。

上述为源码局部抽查，未重做安装验收。主工作区还有专家与工作流收敛改动；实施时必须重新确定累计基线和接口，不用本文件中的观察覆盖正在进行的实现。

## 2. 核心决策

将协作任务演进为一个持久的、允许在执行中补充要求的任务实例。用户通过统一任务协调助手沟通；协调助手提出结构化计划变更；宿主服务校验、保存并驱动现有调度器执行。任务界面采用现代化协作工作台，把实际专家分工、并行工作、成果交接和下一步操作呈现出来。

本功能必须交付一条完整链路：需求创建 → 推荐初始团队 → 并行执行 → 用户追加要求 → 分析影响 → 局部调整计划并按需增加专家 → 继续执行 → 验收交付 → 显式保存可复用工作流。

## 3. 对象和架构归属

| 对象 | 责任与边界 |
| --- | --- |
| Expert | 专业方法和交付标准；不再另建重复的角色身份库 |
| Responsibility | 某项工作需要的职责或能力，可绑定专家；不是一份新的专家资产 |
| Workflow | 可复用方法：职责、步骤、依赖、验收、允许的动态调整规则；不包含本次私人路径和授权 |
| Mission | 本次需求、计划版本、团队、指令、授权、预算、执行和交付的唯一宿主实例 |
| Task / Attempt | 工作单元及其具体执行尝试；每次尝试固定自己的输入、专家版本、执行配置与授权依据 |
| Coordinator | Mission 的协调职责，使用现有服务模型配置；不强制新增一个与架构师/产品专家重复的专家包 |

临时生成的方法留在任务私有存储。只有用户明确保存为工作流时，才进入“我的能力”；提取时清除实例路径、私有对话、凭据、授权和执行历史。

普通确定性工作流继续走适合自身的轻量执行路径，共享必要的状态和结果展示；本次不强制所有工作流改造成专家团队 Mission。

## 4. 运行中沟通与变更

### 4.1 三类输入

1. **询问**：查询进展、解释等待、询问方案；不自动修改计划。
2. **指令**：用户明确要求变更目标、优先级、任务或实现约束；进入影响分析。
3. **观察**：专家发现问题、测试失败、外部证据；作为事实输入，不能冒充用户指令或授权。

自然语言入口保持统一，不要求用户学习三种模式。宿主保存明确的处理结果：已回答、正在分析、待确认、已应用、部分生效、未应用或失败。表达确实含糊且会改变执行范围时，协调助手澄清；状态查询、明确常规指令不增加无意义的确认。

对话回复必须引用已观测状态。无法确认执行器实时状态时说清楚“正在核实”，不能把计划意图写成已执行事实。只记录任务沟通、决策摘要、工具活动和证据，不展示或索取模型私有思维链。

### 4.2 计划变更是明确的持久对象

变更至少记录：请求身份和来源、幂等键、基于的计划版本及摘要、要求和原因、增删改任务与依赖、专家/执行配置差异、验收差异、受影响产物、范围与预算变化、进行中工作的处理方式、生效状态和确认依据。

变更过程为：接收 → 分析影响 → 校验/必要确认 → 提交计划差异 → 重调度 → 反馈实际生效结果。用户可以在待确认阶段撤回建议。已经生效的变更通过新的补偿变更纠正，不伪装成外部副作用已经回滚。

采用最小必要的版本化持久记录和既有事件能力，不以此另建通用事件溯源平台。对话生成与模型调用在长事务和派发锁之外执行。

### 4.3 明确权限与自主程度

创建时保留需求、工作区、授权三项基础输入；“自动调度”在高级设置中可选择：

- 自动调整：在已授权目标、范围、执行器/服务选择规则、预算及副作用许可内，允许安排/替换专家、拆分任务和局部返工；默认推荐。
- 调整前确认：结构性计划变更先给用户看差异。

两种策略都复用已有授权，常规操作不重复请求。操作系统访问能力 full_access 与“允许自动调整任务”分别表达，不能用其中一个推导另一个。用户明确扩大范围时，保存对应授权变化；系统和专家不能替用户扩大授权。

扩大文件/外部系统访问、超出现有预算、切换到未允许的执行服务、引入未授权外部副作用等，由宿主按已有有效授权判断是否还需确认。确认只覆盖变化部分，不要求重新批准全部已完成工作。

预算不足时仍能查询状态、暂停、取消和追加预算。协调助手的模型用量同样入账；无法继续调用模型时，管理入口通过确定性状态与操作保持可用。

## 5. 动态派活与计划一致性

### 5.1 两层动态能力均纳入本功能

- **延迟绑定**：先定义职责与交付，任务进入可执行状态前，从可用专家库选出适合专家和兼容执行配置，并固定版本。
- **增量重规划**：用户追加要求或执行发现问题后，增加任务、调整未开始的任务/依赖，必要时增加职责和专家。

不把“全量替换计划时拒绝活跃尝试”的保护简单删掉；新增可校验的增量变更通路。旧有整体替换与失败返工语义保留，按明确契约接入。

### 5.2 派发约束

1. 先确定工作需要的能力，再选择专家；同一专家可承担多个兼容工作，不为展示凑人数。
2. 专家来自真实可用目录；派发前固定版本、技能、执行器/服务/模型、任务规格和输入候选。缺失或不兼容时明确等待，不虚构专家或静默换模型。
3. 多个任务可以使用同一专家定义，但执行上下文、输出和 Attempt 相互独立；要求独立验收时保持验收实例隔离。
4. 只对已满足依赖、资源兼容、有预算和执行容量的 ready 集合并行派发，沿用现有隔离写入和整合策略。
5. 自动拆分、重规划和返工设置可解释的上限；重复失败、无进展或目标歧义触发明确反馈，避免持续自我扩张。

### 5.3 正在进行的工作

- 无关分支继续执行；不能因为出现一个待确认变更就全局暂停。
- 受影响且未启动的任务立即停止旧版本派发，在变更生效后重新排队。
- 受影响且正在执行的任务，根据适配器真实能力选择安全检查点接收指令、收尾后调整，或取消并重启。UI 明示生效时机。
- 本功能不承诺所有执行器原生支持会话中途注入；能力不支持时采用可验证的收尾/取消重派路径。
- 停止/取消请求走已有控制链路，不被协调模型的长回复阻塞。进程停止确认前不提前释放冲突资源。

### 5.4 版本、晚到结果与恢复

不能用“Mission 最新版本变化”作为丢弃所有旧尝试事件的条件。Attempt 固定其执行规格、输入和专家版本；旧版本启动的无关分支仍可被接纳。是否采纳结果取决于当前任务需求和输入候选是否仍兼容，已取消或已失效的尝试不能覆盖新状态。

变更以期望版本/摘要做并发校验，提交前重算实际影响；旧客户端和过期提案不能覆盖新计划。相同幂等键重复提交只产生一次变更和派发。提交计划与生成调度意图保持原子性或可恢复对账，确保宿主重启后不漏派、不重复派。

新要求只使受影响的产物及下游验收失效；旧证据保留并标明适用版本。最终验收必须覆盖当前要求和实际整合候选，不能直接沿用已经失效的成功结论。

已完成/已取消的任务不因一句聊天被自动重开。用户明确要求继续扩展时，建立关联后续任务，引用已验收成果，重新核对范围；保留原完成记录。

## 6. 信息架构与现代化可视化

### 6.1 顶层收敛

- “我的任务”：任务实例；按需处理、进行中、已结束组织，普通任务与协作任务沿用统一任务中心。
- “我的能力”：专家、技能、可复用工作流；不混入临时任务和验收测试生成物。
- 三类创建入口：Agent 创建弹窗、AI 客户端技能/MCP、从工作流复用启动；进入同一应用服务和任务生命周期。

### 6.2 详情页只保留必要主层级

固定顶部：任务名称、一个明确主状态、一句当前说明、必要时的主要操作，以及简洁的完成/运行数量和最近活动时间。

主体两个页签：

1. **协作**：当前协作分工、进度和依赖；运行中为默认页。
2. **交付**：最终产物、变更摘要、当前候选的验收结论和证据；完成后为默认页。

团队配置、预算明细、计划版本和完整活动记录在按需抽屉或更多菜单中查看。等待用户确认、授权或预算的事项直接出现在顶部附近，不隐藏在高级设置。当前任务详情与协调对话合理复用同一个右侧工作区，避免同时挤出三四列。桌面窗口打开一个正在执行的 Mission 时，默认显示协调助手；“协作/交付”页签只切换任务内容，协调助手与任务详情通过独立的工作区工具切换。关闭使用常见的 X 图标按钮，提供悬停提示和可访问名称。对话记录独立滚动，输入框固定在助手工作区底部；窄窗口覆盖主工作区，不把聊天追加到任务内容下方。计划、专家、活动记录由任务详情工作区按需查看，不在协作主视图底部重复放置入口。

### 6.3 视觉方向：现代、形象、体现真实协作

主视图采用可自动排布的工作分区与任务卡片，依据真实依赖及当前工作组织；并行工作同层展开，成果交接通过少量清晰连线/交接标记表达。配合专家头像或专业图标，使用户看清“谁正在做什么”。完成分组可折叠，大任务默认聚焦当前工作和下一步，保留搜索/列表查看。

卡片只保留：工作名称、负责专家、真实状态、当前活动或等待原因。执行器可用简洁次要标记；服务、模型、token、原始事件等点开再看。同一任务由多个专家协作时，呈现人员关系和交付职责，避免把一个专家头像误当一个运行进程。

采用既有设计 token，建立清晰字体与间距层次、适量留白、克制色彩、柔和表面和连续的状态过渡。专家加入、任务启动、结果交接、状态变化可以有短动画；位置和任务身份稳定，不因每次刷新跳动，不打断滚动和选择。

动画由已确认运行活动或事件驱动。心跳仅表示在线，不能代表任务有进展；连接断开和状态过期有明确提示。避免永久旋转、虚构百分比、随机移动、无数据含义的流光，以及妨碍操作的大量装饰。

工作流编辑页保留完整依赖图；任务运行页可切换依赖查看，但默认不要求用户理解节点画布。先用当前 React 栈做可验证原型，图组件是否引入依实际规模决定，不预先替换框架。

“生态感”通过专家分工、工具能力与成果交接体现。此轮不引入 3D 办公室、虚拟角色走动或复杂社交网络隐喻。

### 6.5 协调对话中的变更卡片

例如用户输入“增加离线运行，界面开发继续”：

> 将增加本地存储和离线验收，并安排软件专家处理。界面开发继续；综合验收将增加离线检查。
>
> 已应用，软件专家正在排队；其余工作继续执行。

需要确认时卡片显示具体差异及“应用变更”；执行器无法立即接收新指令时显示“本步骤结束后生效”。对话不能先宣称已应用，再后台尝试写入。

## 7. 状态投影与多客户端契约

继续以宿主持久状态和现有快照机制为事实源。UI、协调助手和 MCP 消费同一状态语义，必要时演进版本化投影，而不是各自重新推导。

用户可区分：正在执行、等待具体前置任务、等待资源、正在验收、等待你的确认、预算不足、暂停收尾、失败、完成。多分支部分受阻时同时说明仍在执行的工作和受阻分支，不把局部等待误写成全局停止。

协调助手状态独立于任务执行状态：助手正在回复不等于工作正在执行。UI 同时准确说明对话/变更是否处理中与任务实际进展。

多客户端共用以下语义能力，具体命名在盘点既有 MCP 后确定：

- 读取快照、当前计划、变更和对话上下文。
- 提交消息/明确指令，返回持久请求身份和处理状态。
- 提出、读取、必要时确认、应用或撤回计划变更。
- 查询专家与执行选项，调整未执行工作的指派。
- 订阅或增量读取事件；保留原有预算、暂停、取消和恢复操作。

沿用异步应用服务/任务机制；MCP 重连不导致重复模型调用或重复执行。调用者来源与可信人类授权依据由宿主记录，不能信任模型自己填的“用户已批准”字段。Agent UI 是操作界面，生产流程不依赖 UI 自动点击。

## 8. 替代方案与取舍

| 方案 | 取舍 |
| --- | --- |
| 只整理文案与卡片 | 能改善首屏，但无法支持运行时需求变更，不能完成本功能闭环 |
| 只增加聊天，直接把消息转发给当前 worker | 难以判定生效、无法统一多执行器、容易出现计划与实际脱节 |
| 每次需求变化都停全队并替换整个计划 | 容易复用现有约束，但浪费无关工作，削弱并行体验 |
| 全自主自由组队和任意改计划 | 目标、授权和验收难以控制，采用有边界的动态调度 |
| 默认展示完整 DAG 和全部事件 | 调试信息充分，但日常理解成本高；改为简洁协作视图与按需详情 |
| 引入独立协调平台或新团队资产系统 | 重复 Mission/Workflow 能力，扩大范围；演进现有宿主服务 |

收益：需求逐渐明确时任务可持续推进；更少预配置；更直观地理解团队协作；跨客户端获得一致控制能力。

代价：必须处理计划与尝试的版本共存、变更事务和受影响证据失效；可视化不能掩盖执行适配器的真实能力限制。

## 9. 实施顺序和边界

| 阶段 | 交付与退出条件 |
| --- | --- |
| P0 现状与契约 | 确认主工作区累计基线、已完成与在途功能；落实正式 ADR、变更授权策略及退出条件；与专家/工作流收敛和独立 UI 工作衔接 |
| P1 状态与视觉原型 | 统一用户状态语义；展示并行、局部等待、变更、验收、完成和大任务折叠；提供可交互原型或真实页面效果，并完成组件边界 |
| P2 对话与增量变更 | 持久沟通/指令、影响分析、必要确认和实际生效反馈；无关工作继续，受影响任务可靠调整；UI/MCP 共用通路 |
| P3 动态指派与可靠性 | 运行中选择/增加/替换专家，派发前固定版本；支持真实适配器能力降级；幂等、过期提案、取消晚到结果、重启恢复和受影响验收 |
| P4 完整验收与部署 | 完成下列真实场景与必要回归；部署同一已验证产物；安装版状态、跨客户端与跨执行器证据齐全后收尾 |

P1 先确定视觉方向并行推进基础组件，P2/P3 按共享契约衔接。分阶段交付不能把只有聊天原型的版本宣称为完整动态协作功能。

范围不包括：分布式多宿主调度、重写所有执行适配器、全量工作流重构、3D 虚拟办公室、模型私有思维展示、读屏和 200% 缩放专项。依赖未变化的历史验证按仓库策略核实后可复用，失效部分必须重跑，不另建大型验收框架。

## 10. 可直接验收的场景

| 编号 | 操作 | 通过标准 |
| --- | --- | --- |
| A1 需求入口 | Agent 输入需求/工作区/授权，默认组队；从 Codex 技能/MCP 重试同一请求 | 同一 Mission、同一计划与授权，幂等不重复；真实目录选项，无须先选齐所有专家 |
| A2 并行工作台 | 两个独立任务执行，第三个等待依赖 | 能直接看清谁在工作、谁在等谁、要不要操作；展示有真实时间重叠证据，无虚假百分比 |
| A3 运行中询问 | 执行中问“为什么测试还没开始” | 引用真实依赖和状态，询问不修改计划、不阻塞 worker，助手回复状态与执行状态分开 |
| A4 新要求动态组队 | 界面开发执行时增加离线运行要求 | 形成明确变更，按能力增加存储实现与离线验收、指派可用专家；无关界面分支继续，变更状态可见 |
| A5 生效时机 | 给不支持中途注入的执行器追加要求 | 明示收尾后生效或取消重派；实际不重复写入；界面不虚报已注入 |
| A6 授权差异 | 请求超出现有授权的路径或外部操作 | 只呈现新增范围与影响；确认前不执行新增范围，无关分支继续；已有授权内操作不重复询问 |
| A7 多客户端冲突 | UI 与 MCP 同时基于旧版本提交不同变更，重放同一请求 | 过期提案不覆盖新计划；同请求只生效一次；对话、计划、预算和派发均无重复 |
| A8 版本共存 | 新计划生效后，无关旧版本任务完成；被替换任务晚到结果 | 无关结果可按任务签名接纳；失效/取消尝试不能覆盖新状态；历史证据可追溯 |
| A9 局部验收失效 | 已完成一项检查后新增影响其中一部分的要求 | 保留可信无关结果；受影响产物和下游验收重新验证；最终针对当前要求与整合候选 |
| A10 缺失专家或资源 | 推荐能力无已安装专家，或写资源冲突 | 展示缺什么/等谁和处理入口；不虚构专家、静默切模型或偷偷并行写共享目录 |
| A11 取消、恢复与预算 | 在变更分析或执行中取消/重启；耗尽后追加预算 | 控制链路可用；进程和派发可对账，无重复副作用；预算入账、增额后继续同一有效计划 |
| A12 真实跨执行器 | 安装版混用 HiMind AI 与 Codex，实现中追加要求并完成交付 | 存在真实执行及变更证据；最终产物由当前候选验收；UI/MCP 看到一致结果 |
| A13 工作流沉淀 | 临时协作完成后保存方法并在新项目启动 | 临时方法不出现在“我的能力”；保存后可复用，无私人路径/授权泄漏，旧任务不被改写 |
| A14 视觉与完成态 | 正常窗口查看执行、局部等待、确认、失败、完成及大量任务 | 用户首屏能说明状态/工作/操作；原型与真实页面一致；选择和滚动稳定、连接断开有提示；完成优先展示交付 |

真实验收任务仅操作隔离测试工作区，不能与本功能开发同时写主源码。采用现有 E2E 手段和测试设施优先，computer-use 仅在确有必要时使用。沿用仓库定向验证和产物身份策略，明确哪些检查本轮执行、哪些复用及其理由。

## 13. 实施期桌面信息架构补充（2026-11-17）

用户明确指出这是桌面软件，协调助手不能追加在长页面最底部。由此细化第 6 节：

- 当前任务占满桌面窗口剩余区域，不重复展示任务列表页的大标题。顶部只保留返回、一个主状态、任务标题、一句说明、完成数量/实际并发和主要操作；阶段轨迹和诊断身份移入详情。
- 主体仍为「协作 / 交付」。任务分区独立滚动，大量任务不撑高整个窗口。
- 协作/交付是内容页签；协调助手/任务详情是独立工作区工具，首次打开运行中任务默认进入协调助手。右侧工作区与任务执行区并列，消息记录滚动，输入区固定在该工作区底部，不进入页面纵向内容流。
- 点任务卡片打开该项详情；详情、计划/团队/活动及协调对话复用一个右侧工作区，不同时展开多层侧栏。切换后保留未发送草稿和对话阅读位置，交付页也能继续询问。
- 窗口较窄时面板覆盖工作区右侧，不转为纵向堆叠；顶部待确认、预算或授权提示继续直接可见。面板用带提示和可访问名称的 X 图标关闭。
- 按真实事件更新而非刷新重排；断连或快照过期时不显示已核实并发。静态交互预览与宿主夹具测试分别标明性质，不当作安装版真实协作验收。

本补充是用户对既定方案的细化，未改变 Mission/Workflow 生命周期或本轮 A1–A14 结束条件。
