# 专家协作架构优化实施与验收方案

本方案落实 2026-11-16 已确认的四项产品方向和并行优先要求。
[ADR-0029](adr/0029-expert-team-entry-and-parallel-mission-execution.md) 记录决策；
状态与实际验证记录放在 `.himind/long-tasks/20261116-collaboration-architecture-optimization/`。
本文件描述目标与退出条件，不代表当前安装版已经具有这些能力。

## 产品与对象关系

| 用户概念 | 内部对象与用途 | 运行约束 |
| --- | --- | --- |
| 交给专家团队 | 需求、工作区、访问意图生成任务草案 | UI/MCP 共用应用服务，生成不等于执行 |
| 团队工作流 | 版本化 Workflow，描述可复用职责、方法与验收 | 不包含私人上下文、路径授权或运行历史 |
| 专家团队任务 | Mission，持有本次计划、指派、预算和授权 | 唯一执行所有者，固定定义/专家版本摘要 |
| 子任务 | Task，描述输入、输出、依赖、职责和资源 | 满足依赖且有兼容资源时并发 |
| 执行尝试 | LocalRun，连接执行器与实际产物 | 独立会话、事件、用量、取消和恢复身份 |

专家是专业方法资产；职责是本次工作内容，不另建一套角色身份库。
架构师重叠身份在新任务推荐中收敛；历史原 ID/版本按原定义读取。
通用专家优先覆盖需求与产品、技术架构、软件实现、界面交互、质量验证。
游戏、展项等领域专家按真实工具和验收需求扩展，不为了凑团队人数增加身份。

## 实施阶段

| 阶段 | 修改与产物 | 退出条件 |
| --- | --- | --- |
| P0 基线与契约 | 导出完整已安装专家/版本/开发投影；审查现有 Workflow、Mission、授权与调度；记录 ADR 和迁移计划 | 新旧边界与已验证能力清晰，当前测试入口及回滚点可用 |
| P1 专家与组队推荐 | 确定性版本解析；专家能力分类/重复替代关系；职责必需/可选；推荐团队与兼容执行绑定 | 历史 pin 可读；空壳/缺失能力不会被伪造；无用职责不强制指派 |
| P2 统一需求入口 | Agent/MCP 同一请求与幂等草案服务；选择/生成固定方法；两阶段推荐与确认；默认模型与权限独立 | 不先选 Workflow 也能创建；同请求重试不重复；未确认不派发 |
| P3 并行与候选整合 | ready-set、有界 worker、任务/资源 claim、隔离工作区、幂等整合、候选验收、并行恢复与预算治理 | 存在真实重叠；冲突保护、依赖、取消、重启、预算追加均有证据 |
| P4 任务可视化 | 需求创建弹窗、团队调整、任务中心统一投影；状态/下一步首屏、并行轨道、交付/复核和活动详情 | 用户可区分正在做、等谁、为何等、要不要处理；事件与真实运行一致 |
| P5 安装版交付 | 定向回归、构建、deploy-local、真实 HiMind AI/Codex 跨执行器任务、最终候选核验 | 当前安装产物与源码可追溯；场景通过；人工观感确认；功能分支提交与回滚记录完整 |

P1/P2/P3 的接口先固定再并行开发各自模块；没有依赖的测试、文档、UI 夹具可以并行。
主工作区中的本次开发由当前 Codex Goal 唯一持有；运行时验收只写独立测试目录。
先完成只读并发，再开放经过验证的隔离写并发；不能把第一步通过当作并行写能力完成。

## 并行调度规则

- 只声明真正的产物/验收依赖；无依赖任务进入 ready 集合，不按专家角色顺序排队。
- 新计划默认有界并发，初值 3，可配置；受执行器会话容量、服务限流和共享预算共同约束。
- 专家包可复用，但每个并行任务有独立执行实例和上下文；实现与独立验收使用不同实例。
- 只读分析共享同一不可变基线；独立报告写到各自输出目录，不能把写报告误作只读共享。
- 写任务优先在隔离 worktree/工作区运行；按实际修改验证授权范围后整合，不直接并发改主目录。
- 同文件/父子目录冲突、构建目录、端口、设备、数据库和外部副作用采用资源声明及租约。
- 合并后的候选单独固定摘要；整合冲突产生明确待办；各分支成功不替代整合后的验收。
- 一个分支失败/等待复核只阻塞相关下游；无关任务按已确认失败策略继续。
- 并发预算有原子预留/结算和延迟上报说明；未知用量不能按零计；增额继续保留原历史。
- 取消和宿主重启对账每个活动尝试，未确认实际停机不能释放冲突资源或重新执行副作用。

本次实现边界：新计划默认上限 3；有有限 token/金额预算时暂降为 1，不声称已有执行器硬预留。
同一 Mission 的一轮调度仍由单一 OS 锁所有者组织，轮内 worker 并行；整合与复核冻结共享候选。
写入隔离仅支持干净完整 Git，未跟踪/忽略输入、子模块、非 Git 或脏工作区降级串行并说明；
整合暂拒绝删除，保留隔离目录供恢复。上述边界是本次交付限制，不计为已支持场景。

MCP 自然语言入口顺序为 `mission.intent.create` → `mission.assignment.options/apply` →
`mission.plan.generate`（当前 `expected_plan_revision`）→ 查看提案 → `mission.plan.confirm`。
同一幂等键重用原任务，生成/推荐均不启动；原有精确 Workflow pin 的 `mission.handoff.create`
继续支持导入计划。运行授权以用户已有明确指令及所确认的计划摘要、选集和范围为准。

Mission 的执行尝试禁止从通用 Workflow resume/feedback 直接执行。`mission.control resume`
在调度锁内将当前绑定且由用户暂停的尝试重新入队，再交回原调度器；等待审批、反馈及
外部信号的尝试不因此跳过确认。仍有派发批次运行时明确要求收尾后重试，不抢占执行权。

## 可以直接验收的场景

| 编号 | 需求与操作 | 可以观察和复核的通过标准 |
| --- | --- | --- |
| S01 专家不重复且历史可读 | 目录同时含项目/系统架构师及 UI 专家 1.0、1.1；创建“优化 AI 服务设置页” | 推荐不同时凑入两个重叠架构师；选择有效最新版本不依赖目录遍历；旧 Mission 的 1.0 pin 仍解析原内容，绝不重写为 1.1 |
| S02 自然语言创建 | Agent 输入“审查并优化 AI 服务设置页的信息架构与错误状态”，选择隔离项目、工作区访问、预算，采用默认执行配置 | 用户不必先安装/选择指定团队 Workflow；看到必要职责、专家、执行器/服务/模型和选择理由；创建/默认配置不触发写入；确认最新计划和范围后才派发 |
| S03 从 Codex 接续 | 在 Codex 用技能/MCP 发送 S02 的需求，重复同一幂等键，再到 Agent 打开 | 只产生一条草案；来源、工作区和版本一致；客户端切换看到同一状态；扩大授权显示差异，模型不能因调用 MCP 自行批准 |
| S04 三路审查并行 | 对固定源码基线分别运行 AI 服务架构、信息架构、界面设计审查，再综合方案 | 三个任务启动/结束事件存在真实重叠；综合任务在三个依赖成功后才开始；输出独立；延时夹具中通过同步屏障证明并发，不只看 UI 动画 |
| S05 混合执行器并行实现 | 约定接口后，HiMind AI 改后端校验，Codex 改前端空/错/加载状态；质量专家复核最终候选 | 两个写任务在不同隔离工作区时间重叠；都遵守授权；补丁整合到同一候选；集成检查和独立复核以该候选摘要为准；界面可看见两个执行器的真实活动 |
| S06 同资源冲突 | 两个任务修改同一配置文件，或占用同一端口/设备/构建目录 | 系统明确显示“等待资源，由任务 X 占用”；不会同时写；整合不静默覆盖；释放只在进程停止/结果持久化后发生 |
| S07 局部失败不拖全队 | 审查 A 故意失败；B/C 与 A 无依赖；D 依赖 A | B/C 能继续；D 不启动；A 返工有独立尝试与原失败证据；A 通过后 D 才可运行；任务总状态直白说明部分工作受阻 |
| S08 并发取消与恢复 | S05 运行中取消一个分支并重启宿主；保留另一分支的已交付结果 | 被取消进程停止，晚到事件不覆盖终态；其工作区与资源可安全处理；其他分支结果不丢；已完成副作用不重复；旧进程身份不明时说明待对账原因 |
| S09 预算耗尽与追加 | 以低总预算启动两条分支，使预算达到阈值，再增加预算 | 不再新派发；显示已知用量/预留/未知部分和处理中的任务；一次增额请求幂等；可继续剩余任务，无重复扣账或抹去原失败/取消历史；延迟上报产生的超额有实测说明 |
| S10 成熟方法复用 | 将 S05 成功的团队方式保存为 Workflow，在另一个空白隔离项目执行新需求 | Workflow 固定职责/方法/验收，导出不含私人对话、机器路径或旧授权；新运行重新选择环境和确认；更新 Workflow 后旧 Mission 的定义与证据不变 |
| S11 普通流程兼容 | 运行一个无专家角色的确定性 Workflow，例如构建/上传前检查 | 不强迫指派团队；在任务中心同样能查看状态、待办和交付，仍使用原有执行能力，无第二套调度器 |
| S12 状态首屏与安装版 | 在最终安装版依次查看待确认、并行中、等待资源、复核中、失败、预算不足和完成 | 首屏能说明现在做什么、等谁、要不要操作及交付在哪里；活动动效只用于真运行；“复核中”解释正在检查哪些交付；截屏/交互断言与任务事件一致 |

S04/S06-S09 用可重复的确定性夹具覆盖时序与负例；S02/S03/S05/S10/S12 还需要
真实服务及最终安装版验证。报告明确区分源码测试、模拟执行、真实模型和人工签收。
并行验收记录 attempt、执行器、工作区、输入候选、开始/结束时刻、依赖、资源占用、
交付候选和核验结果。真实任务的模型耗时不用于声称固定加速比。

## 创建和详情页信息架构

创建：需求描述 → 工作区与访问范围 → 生成团队/方法/计划建议 → 可选调整专家与执行配置 →
确认当前计划、授权与预算 → 开始。推荐与确认可在同一个弹窗分步呈现，默认模型按钮只改配置。
工作区读写/完全访问要按执行器实际能力说明；不可用选项解释原因，不静默降低权限或换服务。

详情首屏：任务标题与状态 → 当前工作/等待原因/单一主操作 → 并行轨道与依赖 →
交付及验收进展。专家配置、原始运行协议和完整事件日志按需展开。
完成态以可打开的交付与验收证据为主，不继续突出“恢复/立即检查”等运行期操作。

## 验证策略与收尾

复用现有 Mission/Workflow/浏览器/deploy-local 测试入口，新增测试只覆盖实际行为与风险。
先做参数、版本、授权和并发的定向验证，再运行受影响集成；对于源码、依赖、工具和构建
产物均未变化的成功步骤，核实身份与依赖后复用并标明原始来源，不伪装成本轮执行。
保留最终安装版的真实跨执行器协作、预算追加、进程取消/恢复和 UI 状态验收。

工程预算沿用用户明确提供的 1 万亿 token；本长任务另设 80 轮/960 分钟工程停止边界。
不新增庞大验收框架，不扩大到通用 AI 客户端，不做读屏或 200% 缩放，不推送/公网发布。
源代码在主工作区功能分支提交，主分支不混入未完成变更；部署保留上个可用安装和恢复记录。
